# 小笙助手：从需求讨论到调试发布的完整学习教程

> 适用版本：小笙助手 v0.2.5（2026-10-06 复测版）
> 工程目录：项目根目录
> 面向读者：刚开始学习 Kotlin、Android、网络请求和页面解析的初学者

这份文档记录这几天项目经历的完整过程。它不是只告诉你“最后改了什么”，而是尽量回答下面几个更重要的问题：

- 用户看到的问题，背后通常是哪一层出了错？
- 为什么同一个问题不能只靠改一个按钮或一行代码解决？
- 如何从日志、网页结构和测试结果判断修复是否真实有效？
- 哪些功能是应用可以控制的，哪些功能最终由 Android 系统或学习通页面决定？
- 以后你自己接手代码时，应该从哪里开始读、怎样验证、怎样避免误判？

## 0. 先说明安全边界

真实账号曾经用于本地联调，但本教程**不保存、不展示**账号、密码、Cookie、完整会话令牌，也不放入带 `enc`、`token`、`cpi` 等敏感参数的完整地址。日志中只保留了课程数量、作业数量、HTTP 状态和页面结构等非敏感信息。

这个项目的定位是：

- 只读取学习通课程和作业信息；
- 点击作业后打开官方页面，由用户自己完成；
- 不自动答题、不自动提交、不把 Cookie 上传到第三方服务器；
- 本地业务数据按账号隔离；
- 页面变化时宁可显示“未知”并提示检查，也不随便猜一个截止时间。

这几个边界很重要。一个能抓到数据的程序，不代表它可以安全地自动操作学习通；一个能发出通知的程序，也不代表它可以绕过手机系统设置。

## 1. 我们到底在做什么

小笙助手是一个“学习通作业提醒器”，不是学习通的替代客户端。它把学习通网页中分散的课程、作业、状态和截止时间整理成一个更适合查看的列表。

典型流程如下：

```text
用户在官方登录页登录
        │
        ▼
WebView 获得学习通 Cookie
        │
        ▼
Cookie 只保存到手机 App 私有空间
        │
        ▼
读取课程列表
        │
        ▼
逐门课程读取作业列表
        │
        ▼
必要时沿官方链接打开每条作业详情
        │
        ▼
解析截止时间、完成状态、课程和作业名称
        │
        ▼
缓存、筛选、分组、提醒
```

项目主动不做的事情：

1. 不模拟密码加密登录。学习通登录过程有验证码、加密和风控，直接自己拼登录请求既脆弱又容易触发验证。
2. 不把“课程结束时间”当成“作业截止时间”。这两个概念不同。
3. 不把 HTTP 200 当成“成功抓到作业”。200 也可能返回登录页、空课程页或错误页面。
4. 不因为解析不到时间就编造未来日期。未知值用 `0` 表示，并在界面上显示“截止时间未知”。

## 2. 从工具链开始：Android Studio、JDK、Gradle、SDK 是什么

如果你是新手，可以先把 Android 构建理解成一条流水线：

```text
Kotlin 源码 + XML 布局
          │
          ▼
Kotlin 编译器 / Android Gradle Plugin
          │
          ▼
Java 字节码 + Android 资源
          │
          ▼
Android SDK 工具打包、对齐、签名
          │
          ▼
APK
```

### 2.1 JDK

JDK 是编译 Kotlin/Java 的基础环境。本项目使用 Java 17，源码和 Gradle 的目标版本也是 17。JDK 不是 Android SDK，它负责运行编译器和 Gradle。

本次约定的工具目录是：

```text
D:\JDK17       JDK 17
D:\Gradle      Gradle 或 Gradle 缓存工具
D:\AndroidSDK  Android SDK、平台和构建工具
```

以后如果 Android Studio 报“Java 版本不匹配”，优先检查 Gradle JDK 是否指向 JDK 17，而不是重复安装一堆 SDK。

### 2.2 Gradle 和 Gradle Wrapper

Gradle 是构建系统。项目中的 `gradlew.bat` 是 Gradle Wrapper，它会按照项目锁定的版本运行 Gradle，因此换一台电脑也尽量得到一致的构建结果。

常见命令：

```powershell
cd D:\xxt-build
\.\gradlew.bat testDebugUnitTest
\.\gradlew.bat lintDebug
\.\gradlew.bat assembleDebug
\.\gradlew.bat assembleRelease
```

命令含义：

- `testDebugUnitTest`：运行单元测试；
- `lintDebug`：检查潜在错误、可访问性、资源和代码质量；
- `assembleDebug`：生成可直接安装调试包；
- `assembleRelease`：生成发布构建，但没有正式签名证书时仍然可能是未签名文件。

### 2.3 Android SDK、compileSdk、minSdk、targetSdk

`app/build.gradle.kts` 中当前关键值是：

```kotlin
compileSdk = 34
minSdk = 26
targetSdk = 34
```

- `compileSdk`：编译时可以使用哪些 Android API；
- `minSdk`：最低支持哪个 Android 版本，本项目最低为 Android 8.0；
- `targetSdk`：告诉系统这个应用按照哪个版本的行为约定开发。目标 34 意味着必须认真处理 Android 13 的通知权限等新规则。

### 2.4 当前主要依赖

本项目没有引入复杂的第三方网络爬虫库，主要使用 Android 官方或常见基础库：

- AppCompat：兼容不同 Android 版本；
- Material：按钮、对话框和基础视觉组件；
- RecyclerView：高效显示可滚动作业列表；
- WorkManager：安排后台提醒任务；
- JUnit：运行纯 Kotlin 单元测试。

## 4. Android 基础概念：Activity、WebView、RecyclerView、Adapter

### 4.1 Activity 是一个页面控制器

`LoginActivity`、`MainActivity` 和 `HomeworkDetailActivity` 都是 Activity。可以把 Activity 理解成一个页面的控制器，它负责：

1. 加载布局；
2. 监听按钮和列表点击；
3. 调用数据层；
4. 在页面生命周期变化时保存或恢复状态。

常见生命周期顺序是：

```text
onCreate → onStart → onResume
                         │
                    用户切到别处
                         │
                   onPause → onStop
```

以前“每次打开都自动刷新”的问题，正是因为把网络抓取放在了容易重复触发的生命周期回调里。后面会专门解释。

### 4.2 WebView 是应用内浏览器

登录和打开作业详情都使用 WebView。它不是一个截图控件，而是一个真正能加载网页、执行网页脚本、保存 Cookie 的浏览器内核。

项目使用 WebView 登录的原因：

- 登录页面的加密、验证码和风控由官方页面自己处理；
- 用户可以在官方页面完成滑块或图片验证；
- App 只读取已经产生的会话 Cookie，不记录密码；
- 作业详情仍由官方网页展示，提交动作由用户自己完成。

### 4.3 RecyclerView 和 Adapter

RecyclerView 是滚动列表容器，Adapter 负责把一条 `Homework` 数据转换成一个列表卡片。

```text
List<Homework>
       │
       ▼
HomeworkAdapter
       │
       ▼
item_homework.xml / 课程分组标题
```

当排序、状态颜色或双列布局出现问题时，不应该只修改 XML。要同时检查：

- `MainActivity` 传给 Adapter 的数据顺序；
- Adapter 是否正确识别分组标题和作业行；
- `GridLayoutManager` 的 span size 是否让课程标题占满一行；
- 横屏或窄屏时文字是否会互相覆盖。

## 5. 登录流程：为什么不是“记住密码”，而是保存 Cookie

### 5.1 Cookie 是什么

登录成功后，服务器会给浏览器一组会话凭证。浏览器以后请求学习通页面时自动带上它们，服务器由此知道“这是已经登录的用户”。这些键值对就是 Cookie。

本项目的 `AccountManager` 只在 App 私有存储中保存 Cookie，存储结构类似：

```text
uid → 该 uid 对应的一组 Cookie
```

这里的 `uid` 是学习通会话中能识别账号的稳定标识，不是把密码保存下来。

### 5.2 为什么要访问多个域名

学习通不同页面可能使用不同子域，例如登录站、课程站、作业站和 API 站。浏览器访问一个域名时，服务器可能只给该域设置 Cookie；如果 App 只拿登录页的 Cookie，课程接口可能返回空、400 或跳转登录。

当前 `LoginActivity` 的逻辑是：

```text
发现登录 Cookie 中有有效 uid
        │
        ├─ 访问主站，让主站 Cookie 完整
        ├─ 访问课程站，让 mooc1 Cookie 完整
        ├─ 访问课程 API，让 API 域 route/JSESSIONID/token 完整
        └─ 收集多个域的 Cookie，按账号保存
```

这解决了第一轮复测中的一个关键问题：**网页上明明已经登录，但 API 侧认为没有会话**。

### 5.3 Cookie 合并时为什么要去重

不同域可能存在同名 Cookie，例如 `route` 或会话标记。如果把同名字段原样拼在一起，服务器可能读取到旧值。`XueXiTongApi` 会把 Cookie 按名称放入 `LinkedHashMap`，后出现的值覆盖前一个值，再生成请求头。

这不是为了“伪造登录”，而是模拟浏览器对当前会话的最后有效值。

### 5.4 登录成功不能只看 HTTP 200

一个失效会话访问课程接口时，服务器可能返回 302，然后跳转到登录 HTML。登录页本身也可能是 HTTP 200。所以判断登录是否有效要综合：

- Cookie 是否有有效 uid；
- 返回页面是不是登录页；
- 返回 JSON 是否包含课程数据结构；
- 页面是否包含明确的登录表单特征。

如果误把登录页当课程列表，用户看到的就会是“0 门课程”，随后所有作业都会变成“未知”或空列表。这是之前排查出的真实根因之一。

### 5.5 退出登录和账号切换

讨论过程中曾经出现“添加账号按钮”，但它容易让用户误以为可以在当前页面无刷新地叠加账号。最终交互方向改为：

- 设置中提供“退出登录”；
- 退出时清除登录凭证和 WebView Cookie；
- 账号对应的本地作业、课程、隐藏和截止时间修改保留在本机；
- 下次登录另一个账号时，数据按新的 uid 隔离。

这样做的好处是入口简单，且不会把旧账号的作业或提醒串到新账号上。

## 6. 从课程到作业：抓取链路怎样工作

### 6.1 第一步：课程列表

当前实测课程入口是学习通官方页面实际使用的课程接口。成功响应解析出课程对象，课程对象至少需要：

- 课程显示名；
- `courseId`；
- `classId` 或 `clazzid`；
- `cpi`；
- 用于回到课程网页的入口信息。

重要提醒：课程节点里的某个 `id` 不一定就是 `courseId`。解析器应优先从课程入口 URL 或明确命名字段取值，不能看到一个数字就直接猜它的含义。

### 6.2 第二步：过滤已经结束的课程

课程列表中可能有上一学期、模拟测试或已经结束的课程。当前逻辑会先识别课程结束状态，减少无意义请求。

但“结束课程过滤”不能代替日期范围筛选。用户选择某个时间段时，作业是否显示应由作业自己的截止时间决定，而不是由课程名称或课程创建时间决定。

### 6.3 第三步：读取作业列表

主要接口形态为：

```text
GET https://mooc1-api.chaoxing.com/work/task-list?courseId=...&classId=...&cpi=...
```

不同课程和不同会话可能返回：

- JSON 作业数组；
- HTML 作业列表；
- HTML 壳页面；
- 登录页；
- 明确的“暂无作业”页面；
- 错误或风控提示。

因此解析流程不能写成“只要 200 就当成功”。当前代码会检查内容特征，并在日志中记录来源，例如接口是否为 `A_pure`、是否切换到网页版课程入口、页面解析了多少条。

### 6.4 `li[data]` 为什么重要

真实网页中的作业行类似：

```html
<li onclick="goTask(this);"
    data="https://mooc1.chaoxing.com/mooc-ans/mooc2/work/task?...">
    ...作业名称和状态...
</li>
```

这里的 `data` 不是普通装饰属性，而是网页点击作业时要使用的官方入口。它可能包含 `taskrefId`、`workId`、`enc` 等参数。App 应该保留这个官方链接，后续点击时沿官方跳转链进入详情页。

不能这样做：

```text
看到标题“作业 1” → 自己猜一个 workId → 拼一个地址
```

因为不同课程、不同作业、不同会话的参数都可能不同。猜错后会出现打开错误作业、跳回课程页或再次要求登录。

### 6.5 标题和状态的兼容解析

当前网页版本中，标题常出现在 `overHidden2` 元素里，状态可能出现在 `p.status`，旧页面又可能使用普通 `p` 和 `span`。所以 `XueXiTongApi` 使用多级回退：

1. 优先取 `overHidden2`；
2. 没有时取第一个 `p`；
3. 状态优先取 `p.status`，再结合 `span` 和可见文本；
4. 页面结构都不匹配时，再尝试 JSON 或旧版 `workId` 结构。

这种“宽松解析”不是无条件乱匹配，而是多个明确规则按优先级尝试，并保留日志，方便页面改版后知道是哪一级失效。

## 7. 截止时间：为什么必须打开每条作业详情

### 7.1 列表摘要不一定有最终时间

课程列表或作业列表里可能只有“进行中”“待提交”“剩余若干天”等摘要。真正的作答时间通常在作业详情页，例如页面文字可能呈现：

```text
作答时间：
09-24 16:00
至
09-30 20:00
```

这就是本次真实复测中确认的可靠来源。模拟电子技术、复变函数与积分变换、单片机基础与应用等有作业的课程，逐条打开详情后都能得到明确时间；某门课程显示“暂无作业”则是合法空课程，不是解析失败。

### 7.2 当前的截止时间优先级

解析器应按可信程度从高到低使用来源：

1. 作业详情页“作答时间”的结束时间；
2. 详情页明确命名的 `endTime` 或 `deadline` 字段；
3. 作业列表明确标注的截止时间；
4. 页面明确给出的“剩余 X 天/小时/分钟”换算值；
5. 都没有时保留未知。

课程结束时间、课程发布时间、抓取时间都不能拿来冒充作业截止时间。

### 7.3 无年份日期如何处理

如果页面只有 `09-30 20:00`，解析器需要结合抓取时间和开始日期推断年份。例如：

- 开始日期和结束日期在同一年，使用该年；
- 开始日期在 12 月、结束日期在 1 月，结束时间应视为下一年；
- 推断结果不合理时宁可保留未知，等待用户确认。

绝不能简单地把所有 `MM-DD` 都强行加上当前年份，因为跨年作业会被放到错误日期。

### 7.4 “未知截止时间”的正确含义

未知不是“作业不存在”，而是“目前证据不足以证明具体时间”。常见原因有：

- 会话已失效，拿到的是登录页；
- 课程确实没有作业；
- 列表接口只给摘要，需要逐条进入详情；
- 页面改版，解析规则暂时不认识新结构；
- 服务器触发验证码或风控；
- 作业链接重定向后没有得到有效详情。

当前界面处理原则是：

- 日期范围筛选时，未知项不混进主列表，避免把历史作业带出来；
- 未知项由汇总提示单独列出，让用户知道有多少条、属于哪些课程；
- 一天内只提示一次，用户选择“一天后再提醒”后，不因重新进入应用重复弹窗；
- 用户可以手动设置截止时间；
- 如果以后详情页读到了准确时间，先询问是否恢复为自动时间，不直接覆盖用户的手工修改。

## 8. 深度检查、刷新和任务并发：这次真正修复了什么

### 8.1 为什么以前每次进入页面都会刷新

Android 的 `onResume()` 会在以下场景触发：

- 从别的页面返回；
- 从设置对话框关闭回来；
- 从作业详情页返回；
- App 从后台回到前台；
- 某些系统窗口关闭后恢复。

如果在 `onResume()` 里直接调用网络抓取，就会出现：

```text
进入主页 → 抓取
打开设置 → 返回 → 又抓取
打开作业 → 返回 → 又抓取
切到后台 → 回来 → 又抓取
```

结果是验证码更频繁、旧任务和新任务同时运行、未知截止时间提示反复弹出。

### 8.2 当前刷新策略

当前设计是：

1. 第一次进入账号页面时显示本地缓存；
2. 缓存过期时才允许一次后台刷新；
3. 用户点击“重新检查/刷新”时才强制刷新；
4. 同一个账号同时只能有一个抓取任务；
5. 抓取期间禁用重复刷新按钮；
6. 切换账号时取消旧任务；
7. 任务回调更新界面前再次确认 uid 仍是当前账号。

伪代码可以写成：

```kotlin
fun loadHomework(uid: String, force: Boolean) {
    showCache(uid)

    if (loadInProgress) return
    if (!force && !cache.isStale(uid)) return

    loadInProgress = true
    activeJob = launch {
        val result = api.fetch(uid)
        if (currentUid == uid) {
            cache.save(uid, result)
            render(result)
        }
        loadInProgress = false
    }
}
```

真实代码还需要处理异常、取消、按钮状态和生命周期，但最重要的是最后那句 `currentUid == uid`。没有这项检查，旧账号请求晚一点返回，就可能把旧账号数据画到新账号页面上。

### 8.3 深度检查为什么放在用户主动操作

深度检查会逐条请求作业详情，成本比读取课程摘要更高，也更容易触发验证码。现在把它绑定到用户明确点击的“重新检查”，并在成功后同步当前会话 Cookie。平时打开 App 主要读缓存，不持续扫全站。

### 8.4 会话失效、空课程和解析失败必须分开

这是这次排查中最关键的思维方式：

| 现象 | 真实含义 | 正确处理 |
|---|---|---|
| 302 跳登录页 | 会话失效 | 提示重新验证，不显示为 0 门课程 |
| 页面明确“暂无作业” | 课程合法为空 | 记录成功，作业数为 0 |
| HTML 有作业行但解析为 0 | 解析规则落后 | 保留页面样本，修解析器 |
| 400/403 且有风控提示 | Cookie/验证/参数问题 | 单课失败隔离，提示重新检查 |
| HTTP 200 但内容是登录 HTML | 不能视为成功 | 检查页面特征后标记会话问题 |

如果把这几类都写成“解析失败”，日志会误导开发者，用户也会觉得“课程越来越多未知”。

## 9. 本地缓存、手动作业、课程库和隐藏功能

### 9.1 为什么需要缓存

网络抓取可能需要几十秒，也可能暂时失败。`HomeworkCache` 在手机私有空间保存上一次成功的自动作业：

```text
打开主页 → 立即显示缓存
             │
             └→ 需要时后台更新
```

这样用户不会因为一次网络波动看到空白页面，也不会因为返回主页就立即再次请求。

缓存同时记录保存时间和最近一次尝试时间，用于判断是否过期和是否处于冷却期。

### 9.2 手动作业和自动作业要分开

有些老师会在线下布置作业，学习通没有对应作业。`ManualHomeworkStore` 保存这类作业，并给它们生成类似 `manual_时间戳` 的本地 ID。

手动作业有几个特点：

- 没有学习通 URL；
- 截止时间由用户输入；
- 完成状态只能由用户在 App 内点击切换；
- 仍然参与排序、提醒和隐藏。

它不能和自动作业混用同一套服务器状态。用户把手动作业标记为完成，只代表本地记录完成，不代表学习通服务器已经提交。

### 9.3 课程库的意义

课程独立保存后，即使某门课程当前没有作业，也可以在手动添加作业时复用课程名称。课程稳定键优先由 `courseId + classId` 组成；手动课程使用本地生成的稳定键。

这个设计解决了“课程没有作业，所以添加作业时没有课程可选”的问题。

### 9.4 隐藏和恢复

隐藏不是删除。`HiddenStore` 会记录：

- 账号；
- 作业或课程稳定键；
- 隐藏范围；
- 隐藏时间；
- 作业来源。

设置里的恢复页面可以查看隐藏项，避免用户误操作后永远找不回来。

### 9.5 作业状态与欠账区

当前模型有三个主要状态：

- `PENDING`：未完成，通常需要提醒；
- `SUBMITTED`：已提交、待批阅；
- `DONE`：已完成或已批阅。

当状态是未完成且截止时间已经过去时，`Homework.isMissed()` 将它视为欠账作业。未知截止时间的已完成作业不应被放进欠账区，因为没有证据证明它逾期。

## 10. 时间范围、课程分组和列表布局

### 10.1 时间范围过滤

`HomeworkScope.contains()` 的规则很简单但很重要：

```text
选择“全部” → 所有符合其他条件的作业可见
选择具体日期范围 → 只有 endTime > 0 且落在范围内的作业可见
未知 endTime → 不进入日期范围主列表
```

这样可以避免用户选择未来一周时，历史课程因为“未知截止时间”被错误混入结果。

日期边界建议使用当天的开始和结束时间，避免把当天晚上的作业漏掉。测试时要特别检查：

- 起始日 00:00 是否包含；
- 结束日 23:59:59 是否包含；
- 本地时区是否为 Asia/Shanghai；
- 夏令时变化地区是否需要额外处理。

### 10.2 分组和收起

课程分组时，课程标题是分组项，作业是子项。折叠状态应该按课程稳定键保存，而不是按列表位置保存，因为排序或筛选会改变位置。

### 10.3 双列布局的正确含义

讨论中明确过：双列是“一个课程内部的作业双列”，不是把课程分组标题也拆成两列。实现上通常用 `GridLayoutManager`：

```text
课程标题：spanSize = 2，占满一行
作业卡片：spanSize = 1，左右各一张
```

未开启课程分组时，默认列表仍应按单列展示；布局选择保存后必须真正作用到 RecyclerView，而不是只改变设置对话框中的勾选状态。这类问题要用截图和 UI 层级检查验证，不能只看 SharedPreferences 里是否存了值。

### 10.4 课程选择排序

课程选择器可以有两种排序方式：

- 最近使用/最近添加；
- 拼音首字母。

拼音索引时，数字和特殊字符归到 `#`。右侧 A-Z-# 快速索引属于 UI 辅助功能，必须和实际列表排序共用同一套分组规则，否则用户点击 A 可能跳到错误位置。

## 11. 通知、锁屏和后台：哪些能做，哪些不能保证

### 11.1 通知链路

一条提醒大致经过：

```text
截止时间 - 提前节点
          │
          ▼
ReminderScheduler 安排任务
          │
          ├─ 普通模式：WorkManager
          └─ 精确模式：AlarmManager 精确闹钟
          │
          ▼
ReminderWorker 或 ExactReminderReceiver
          │
          ▼
ReminderNotifier 构造 Notification
```

`ReminderNotifier` 当前会设置：

- 高重要性通知频道；
- 默认系统通知声音；
- 震动；
- `VISIBILITY_PUBLIC`，具备在锁屏公开显示的资格；
- 点击通知后回到作业详情或主页。

### 11.2 Android 13 通知权限

Android 13 及以上，新安装应用的通知默认可能关闭。Manifest 中声明 `POST_NOTIFICATIONS` 还不够，必须在运行时请求权限。用户拒绝后，App 不能偷偷重新打开，只能引导用户去系统设置。

所以“点发送测试通知后没有声音”至少要检查：

1. App 总通知是否开启；
2. 作业截止提醒频道是否开启；
3. 频道重要性是不是高或默认；
4. 频道声音是不是被用户静音；
5. 手机通知音量、勿扰模式和静音状态；
6. 锁屏通知是否允许显示；
7. 厂商是否限制后台运行。

### 11.3 为什么改了频道代码，旧手机仍然无声

Android 8.0 以后，通知频道第一次创建后，重要性、声音等关键行为主要由系统和用户控制。App 再次调用 `createNotificationChannel()` 不一定能覆盖用户已经做过的设置。

这也是当前使用版本化频道 ID（例如 `homework_deadline_v3`）的原因：升级时创建一个新的频道，避免旧版测试期间被静音的频道继续影响新版本。但用户仍然拥有最终控制权。

### 11.4 WorkManager 和 AlarmManager 的区别

- WorkManager：适合可靠但不要求秒级精确的后台工作，系统可能因 Doze、省电和厂商策略稍微延迟；
- `setAndAllowWhileIdle()`：允许低电耗期间较快触发，但仍不是严格秒级；
- `setExactAndAllowWhileIdle()`：精度更高，适合用户明确打开“精确闹钟模式”的场景，但 Android 12+ 需要“闹钟与提醒”特殊权限，也更耗电。

当前设计默认普通模式，设置中开启精确模式后才尝试精确闹钟。重启、应用升级、权限恢复和时间变化后都需要重新安排提醒。

### 11.5 锁屏通知的真实边界

应用不能强制绕过：

- 系统通知总开关；
- 用户关闭的通知频道；
- 勿扰模式；
- 通知音量为零；
- 锁屏隐私设置；
- 厂商电池优化和后台限制；
- 用户没有授予精确闹钟权限。

因此本项目可以“设置正确的通知资格并检测问题”，但不能在没有目标真机的情况下声称“任何手机黑屏都一定响”。本轮只有模拟器 `emulator-5554`，真实手机的扬声器、锁屏策略和厂商后台限制还必须由目标手机验收。

## 12. 这几天的需求讨论：从现象到方案

下面按时间顺序总结讨论过的主要问题。这里的“已验证”只表示当前源码和复测记录已覆盖，不代表 Android 系统边界被强行解决。

| 讨论中的现象 | 根因或风险 | 形成的方案 | 当前状态 |
|---|---|---|---|
| 添加账号后跳回旧页面、没有真正添加 | 账号入口和页面刷新逻辑耦合 | 去掉添加账号按钮，设置中退出登录后重新登录 | 已实现方向 |
| 每次返回主页都自动刷新 | `onResume()` 重复触发抓取 | 缓存优先、手动刷新、过期才刷新、单任务锁 | 已实现并复测 |
| 旧账号任务混入新账号 | 异步任务晚返回且没有 uid 校验 | 取消旧任务，回调更新前确认当前 uid | 已实现并复测 |
| 划掉后台后需要重新登录 | Cookie 没有可靠持久化 | WebView Cookie 收集后按 uid 本地保存 | 已实现并复测 |
| 课程太多但作业时间未知 | 把列表摘要当最终时间，或拿到登录页 | 逐条沿官方链接访问详情页 | 已实现并复测 |
| 去年的作业被带入新日期范围 | 未知截止时间混入筛选结果 | 日期范围内排除未知项，未知项独立汇总 | 已实现并复测 |
| 未知截止时间反复弹窗 | 每次刷新都当成新提示 | 每账号/作业记录提示时间，一天内不重复 | 已实现方向 |
| 用户手工改时间后自动时间覆盖 | 自动数据和用户覆盖没有区分 | 保存 officialEndTime 与 deadlineOverridden，恢复前询问 | 已实现方向 |
| 课程没有作业，手动添加无法选课程 | 课程库依赖作业列表 | 独立保存课程，支持手动课程 | 已实现方向 |
| 按课程分组不能收起 | 分组标题和作业列表状态没有分离 | 按课程稳定键保存折叠状态 | 已实现方向 |
| 双列看起来把课程也拆开 | Grid span 设置错误 | 课程标题占满一行，课程内部作业双列 | 已实现方向 |
| 作业详情返回后作业消失 | 页面返回触发重新抓取或状态覆盖 | 先展示缓存，回调只更新当前账号，保留旧数据 | 已实现方向 |
| 右滑按钮小、灵敏度低 | 复杂手势在窄卡片上可用性差 | 将关键操作移到菜单，长按用于批量隐藏 | 讨论方案，需按当前界面继续验收 |
| 测试通知亮屏有、锁屏无声 | 频道、权限、系统音量和厂商策略共同决定 | 高重要性频道、锁屏公开、设置引导和真机测试 | App 可控部分已实现，真机仍需验收 |
| 课程选择不易查找 | 长列表缺少稳定排序和索引 | 最近使用/拼音 A-Z-#，右侧快速索引 | 需要单独 UI 回归验收 |
| 图片验证码需要网页验证 | 风控属于学习通服务端 | App 内打开官方验证页，同步 Cookie，用户点击重新检查 | 已实现方向，受官方风控影响 |

这里最值得学习的不是某个按钮，而是处理方式：先把问题分类，再确定它属于业务逻辑、网页结构、异步并发、Android 系统还是外部服务限制。

## 15. 日志阅读入门：看到一行日志应该问什么

建议按下面的顺序判断：

```text
请求是否发出？
   │
   ├─ 没发出 → 刷新按钮、任务锁、生命周期或网络线程问题
   │
   └─ 发出了
        │
        ├─ 302/登录 HTML → 会话失效或 Cookie 域不完整
        ├─ 400/403 → 参数、风控、验证码或 Cookie 问题
        ├─ 200 + 暂无作业 → 合法空课程
        ├─ 200 + 作业 HTML → 进入 HTML 解析
        ├─ 200 + JSON → 进入 JSON 解析
        └─ 200 + 结构不认识 → 页面改版，需要样本和新规则
```

可以保留的日志字段：

- 请求域名和路径，去除敏感查询值；
- HTTP 状态；
- 课程名称；
- 解析到的作业数量；
- 是否检测到登录页；
- 是否发现作答时间字段；
- 解析分支名称；
- 任务开始、结束和取消。

不能写入日志的内容：

- Cookie 完整值；
- 密码；
- 完整 `enc`、`token`、`cpi` 或可复用会话参数；
- 网页中可能包含个人隐私的整页 HTML。

`DebugLog.kt` 中已经有安全限制，日志只用于定位结构问题，不应该变成第二份账号凭证备份。

先确认测试和 Lint 通过，再打开 Android Studio。这样可以把“代码本身的问题”和“设备连接问题”分开。

### 第二步：安装到模拟器或测试机

```powershell
adb devices
adb install -r D:\xxt-build\app\build\outputs\apk\debug\app-debug.apk
```

如果是第一次使用 ADB，先在手机开启开发者选项和 USB 调试。不要把生产账号直接用于未知来源的 APK；测试前确认 APK 来源和代码内容。

### 第三步：观察启动日志

```powershell
adb logcat | Select-String "xxtassistant|AndroidRuntime"
```

遇到崩溃时重点看：

- `FATAL EXCEPTION`；
- 崩溃线程；
- `Caused by` 后的第一处业务代码；
- 是否是权限、资源 ID、网络或 WebView 问题。

### 第四步：按功能顺序测试

建议顺序：

1. 登录页能否打开；
2. 完成官方验证后是否能进入主页；
3. 课程数是否合理；
4. 有作业课程能否解析出作业；
5. 点击“重新检查”时按钮是否防重复；
6. 返回主页是否只读缓存而不自动重复抓取；
7. 日期范围是否排除未知时间；
8. 课程分组能否展开/收起；
9. 手动作业是否能添加、完成、删除；
10. 通知权限、频道声音和锁屏显示是否符合当前手机设置。

## 18. 当前仍然存在的边界和后续工作

下面这些不是“遗漏后可以靠再写几行代码完全消除”的问题，而是需要持续验收或由用户决定的边界：

1. 学习通接口和 HTML 不是稳定公开 API，页面改版后解析器需要维护。
2. 图片验证码、滑块和风控必须由用户在官方页面完成，App 不能安全地绕过。
3. 目标真机锁屏声音尚未在本轮环境中完成最终验收；必须在真实手机上检查通知权限、频道、音量、勿扰、电池策略和锁屏隐私。
4. Release 包仍未使用正式签名证书。正式发布前需要你自己的签名密钥，并妥善备份，不能把密钥提交到仓库。
5. 拼音 A-Z-# 课程索引、长按批量隐藏、时间滚轮等交互，应该用真实手机逐项回归，而不是只看代码里是否存在按钮。
6. 作业提交不由本 App 自动完成。打开详情页后，用户是否能提交取决于学习通当前状态、截止时间和教师设置；过期作业可能只能查看，不能再次提交。

## 20. 可以动手做的练习

为了真正学会，而不是只读文档，建议每次只改一个小点：

1. 在 `Homework.kt` 增加一种状态，并为 `statusText()` 写测试。
2. 给 `HomeworkScope.contains()` 增加“只显示已截止作业”的测试。
3. 在日志中增加“任务取消原因”，但确认不写 Cookie。
4. 在 `CourseStore` 中实现按最近使用排序，再写一个相同课程去重测试。
5. 给详情页解析器添加一条脱敏 HTML 样本，测试跨年日期。
6. 让通知设置页显示当前频道是否静音，并跳转到系统频道设置。
7. 用模拟器测试“旋转屏幕、返回详情页、切换账号”是否会重复抓取。

每完成一个练习，都重复运行：

```powershell
\.\gradlew.bat testDebugUnitTest
\.\gradlew.bat lintDebug
```

如果修改了网页解析器，再补一次真实页面复测，并把结果记录到新的审计文件中，不要只凭“界面看起来正常”下结论。

## 结语：判断“是否真的修好”的方法

以后遇到类似问题，可以用四句话自检：

```text
我看到的现象是什么？
它属于界面、业务、网络、并发还是系统限制？
我改动后是否有可重复的测试证据？
这个结果是代码能保证的，还是需要外部系统/真实设备配合？
```

这四个问题能避免“按钮有了就以为功能完成”“HTTP 200 就以为抓取成功”“模拟器有声音就以为真机一定有声音”这类常见误判。小笙助手这几天的调试过程，本质上就是不断把模糊现象拆成可观察、可测试、可解释的工程问题。
